מעבדה 8: Syslog, ניתוח לוגים וצינור ה-SIEM

יום 5 — ניתוח תוכנות זדוניות ויסודות SIEM
משך: 50 דקות רמה: בינונית סביבה: Kali Linux

מטרות

  • להבין את זרימת הנתונים ב-SIEM: מקורות → איסוף → ניתוח (parsing) → אחסון → אנליזה → פעולה
  • לזהות את מקורות הלוגים הנפוצים ש-SIEM קולט (Windows, Linux, חומת אש, פרוקסי, DNS, EDR, ענן)
  • להגדיר את rsyslog כאוסף לוגים מרכזי המאזין על פורט 514
  • לייצר הודעות syslog ולראות אותן מגיעות לאוסף בזמן אמת
  • לנתח שורת syslog גולמית ל-JSON מנורמל עם שדות בעלי שם
  • להבין את Windows Event Forwarding (WEF), Playbooks של אוטומציית SOAR, וערימת ה-ELK

לפני שמתחילים

מעבדה זו היא 100% מושגית + עבודה מעשית בצנרת לוגים. אין קבצי תוכנה זדונית במעבדה זו, ולכן אין שלב אנטי-וירוס ואין דבר מסוכן להרצה. הכול רץ מקומית על מכונת Kali אחת — מופע rsyslog יחיד מעביר לוגים לעצמו, כך שהוא משחק גם את "מקור הלוגים" וגם את "האוסף המרכזי". אין צורך במכונה וירטואלית שנייה.

יש לך, מוכן לשימוש:

  • מכונת Kali Linux, מופעלת, שולחן עבודה טעון, טרמינל פתוח.
  • משתמש עם הרשאות sudo (משתמש ברירת המחדל של Kali הוא kali, הסיסמה kali).
  • rsyslog כבר מותקן — הוא מגיע כברירת מחדל ב-Kali. (אמת זאת בשלב 2.)
  • כלי שורת הפקודה הסטנדרטיים logger, grep, awk, sed, tail ו-python3 — כולם מותקנים מראש ב-Kali.
כל מה שנעשה במעבדה זו הפיך. שלב 8 מראה כיצד לבטל את שינויי ה-rsyslog ולהחזיר את המכונה בדיוק למצבה הקודם.

שלבי המעבדה

  1. שלב 1 — מושג: זרימת הנתונים ב-SIEM ומקורות הלוגים הנפוצים

    SIEM (Security Information and Event Management) הוא מערכת העצבים המרכזית של ה-SOC. אירועים גולמיים מרחבי הארגון זורמים דרך שישה שלבים:

    1. SOURCES     Devices and apps that emit log events
2. COLLECTION  Logs shipped to one central place (syslog, agents, WEF, APIs)
3. PARSING     Raw text broken into named fields (timestamp, host, src_ip...)
4. STORAGE     Normalized events indexed for fast search (e.g. Elasticsearch)
5. ANALYSIS    Correlation rules, dashboards, alerting on suspicious patterns
6. ACTION      Analyst triage, or automated response via SOAR playbooks

    מעבדה זו עוברת על הצינור משמאל לימין: שלבים 2–4 מכסים איסוף, שלב 5 מכסה ניתוח/נרמול, ושלבים 6–7 מכסים את צד האנליזה והפעולה (WEF, ELK, SOAR).

    SIEM טוב רק כמו הלוגים שמזינים אותו. מקורות לוגים נפוצים:

    מקורמה הוא מספר לךכיצד הוא מגיע ל-SIEM
    Windows Event Logהתחברויות (4624/4625), יצירת תהליכים (4688), שינויי חשבוןסוכן (כגון Winlogbeat) או Windows Event Forwarding (WEF)
    syslog של Linuxהתחברויות SSH, sudo, cron, שגיאות דמון, כשלי אימותהעברה של rsyslog / syslog-ng מעל פורט 514
    חומת אשחיבורים מאושרים/חסומים, סריקות פורטים, כתובות IP חסומותייצוא syslog ממכשיר חומת האש
    פרוקסי אינטרנטכתובות URL שביקרו בהן, קטגוריות חסומות, העלאות גדולות (דליפת מידע)syslog או קובץ לוג שנשלח על ידי סוכן
    שרת DNSחיפושי דומיין — מפתח לזיהוי C2 ו-DNS tunnelingרישום שאילתות DNS שנשלח באמצעות syslog/סוכן
    EDR / אנטי-וירוסזיהויי תוכנה זדונית, עצי תהליכים חשודים, הסגריםAPI ענן של היצרן או מחבר on-prem
    ענן (AWS/Azure/M365)קריאות API, כניסות, שינויי תצורה, גישה ל-S3CloudTrail / Azure Activity / Graph API שה-SIEM מושך
    "מקור לוג" הוא כל דבר שיכול לתאר אירוע בטקסט. הערך של ה-SIEM נובע מהכנסת כולם למקום אחד שניתן לחיפוש, כך שניתן לעקוב אחר פעולה אחת של תוקף בכל אורך חומת האש, ה-DNS ונקודת הקצה בבת אחת.
  2. שלב 2 — הפעלת rsyslog כאוסף מרכזי

    כברירת מחדל rsyslog כותב רק את הלוגים של המכונה המקומית עצמה. נפעיל את הקלט הרשתי שלו כך שיוכל לקבל לוגים ממארחים אחרים על פורט 514 TCP/UDP, ונוסיף תבנית שמתייקת לוגים נכנסים לתוך /var/log/central/.

    תחילה, ודא ש-rsyslog מותקן ופועל:

    systemctl status rsyslog --no-pager
    אתה רואה Active: active (running) בירוק. אם כתוב "inactive", הרץ sudo systemctl start rsyslog.

    צור את התיקייה שבה ינחתו הלוגים המרוכזים:

    sudo mkdir -p /var/log/central

    כעת צור קובץ תצורה ייעודי (נקי יותר מעריכת /etc/rsyslog.conf ישירות — rsyslog טוען אוטומטית את כל מה שב-/etc/rsyslog.d/):

    sudo tee /etc/rsyslog.d/10-central.conf > /dev/null << 'EOF'
# --- Lab 8: central collector ---
# Load the UDP and TCP syslog reception modules
module(load="imudp")
input(type="imudp" port="514")
module(load="imtcp")
input(type="imtcp" port="514")

# Template: one file per sending host under /var/log/central/
template(name="CentralPerHost" type="string"
         string="/var/log/central/%HOSTNAME%.log")

# Route every received message to that template, then stop
*.* ?CentralPerHost
& stop
EOF
    בפריסה אמיתית שורות הקלט הרשתי נמצאות ב-/etc/rsyslog.conf (הן קיימות אך מסומנות כהערה עם #). שימוש בקובץ drop-in בתוך /etc/rsyslog.d/ עושה בדיוק את אותה העבודה וקל להסרה מאוחר יותר.

    בדוק את תחביר התצורה, ואז הפעל מחדש את rsyslog כדי להחיל אותה:

    sudo rsyslogd -N1
sudo systemctl restart rsyslog
    rsyslogd -N1 מדפיס End of config validation run. Bye. ללא שגיאות. לאחר ההפעלה מחדש, systemctl status rsyslog עדיין מציג active (running).

    ודא שהאוסף אכן מאזין על פורט 514:

    sudo ss -lntup | grep 514
    אתה רואה שתי שורות — אחת udp ואחת tcp — שתיהן מחוברות ל-*:514, בבעלות rsyslogd.
    אם ss לא מציג כלום: הרץ שוב sudo rsyslogd -N1 וקרא את השגיאה. הטעות הנפוצה ביותר היא שגיאת הקלדה בשם המודול — הוא חייב להיות imudp ו-imtcp בדיוק. תקן את הקובץ עם sudo nano /etc/rsyslog.d/10-central.conf, ואז הפעל מחדש שוב.
  3. שלב 3 — שליחת לוגי בדיקה לאוסף

    הפקודה logger היא הדרך הסטנדרטית להזריק הודעה ל-syslog. תחילה, הודעה מקומית פשוטה:

    logger "LAB8 hello from the local machine"

    כעת שלח הודעה ברחבי הרשת לאוסף שלנו. -n 127.0.0.1 מכוון למארח (כאן, לעצמנו — loopback), -P 514 מגדיר את הפורט, ו--T כופה TCP:

    logger -n 127.0.0.1 -P 514 -T "LAB8 first message to the collector"

    שלח עוד כמה כדי שיהיה משהו להסתכל עליו:

    logger -n 127.0.0.1 -P 514 -T "LAB8 second test event"
logger -n 127.0.0.1 -P 514 -T -t webproxy "LAB8 user visited example.com"

    בדוק מה נחת בתיקייה המרכזית:

    ls -la /var/log/central/
sudo cat /var/log/central/*.log
    ls מציג קובץ לוג הקרוי על שם שם המארח שלך (למשל kali.log). cat מציג את שלוש הודעות LAB8 ... שלך, כל אחת מקודמת בחותמת זמן ובשם המארח. הודעת -t webproxy מציגה webproxy כתוכנית/תג שלה.
    אם /var/log/central/ ריקה: ההודעה הגיעה ל-rsyslog מקומית אך לא מעל הרשת. בדוק שוב את פלט ss משלב 2. כמו כן ודא שהשתמשת ב--n 127.0.0.1 -P 514 בדיוק — בלי -n, logger כותב רק ל-socket המקומי והתבנית המרכזית לעולם לא רואה את זה.
  4. שלב 4 — צפייה בלוגים מגיעים בזמן אמת

    אנליסטים ב-SOC צופים בלוגים זורמים בזמן אמת. tail -f ("follow") שומר קובץ פתוח ומדפיס שורות חדשות ככל שהן נכתבות. פתח את הלוג המרכזי במצב follow:

    sudo tail -f /var/log/central/*.log

    הטרמינל הזה כעת נחסם וממתין. פתח טרמינל שני (ב-Kali: Ctrl+Shift+T ללשונית חדשה) ושלח אירוע מזויף של כשל התחברות SSH — בדיוק סוג השורה ש-SIEM מחפש לזיהוי brute-force:

    logger -n 127.0.0.1 -P 514 -T -t sshd \
  "Failed password for admin from 192.168.1.100 port 52344 ssh2"

    שלח גם התחברות מוצלחת, כדי שתוכל להשוות:

    logger -n 127.0.0.1 -P 514 -T -t sshd \
  "Accepted password for kali from 10.0.0.5 port 60112 ssh2"
    בטרמינל הראשון, שתי שורות ה-sshd החדשות מופיעות מיידית ככל שאתה שולח אותן — אחת עם Failed password, אחת עם Accepted password. כך בדיוק נראית הזנת SIEM חיה.

    לחץ Ctrl+C בטרמינל הראשון כדי להפסיק את ה-follow.

    חמש שורות Failed password או יותר מאותה כתובת IP מקור בחלון זמן קצר הן כלל הקורלציה הקלאסי להתראת brute-force ב-SSH. ה-SIEM אינו קורא את הטקסט הגולמי — הוא קורא את השדות המנותחים, וזה מה ששלב 5 בונה.
  5. שלב 5 — ניתוח ונרמול: משורה גולמית ל-JSON מנורמל

    שורת syslog גולמית היא רק טקסט. ה-SIEM אינו יכול לקשר "ה-src_ip הזה" עד שהשורה מפורקת לשדות בעלי שם — זהו ניתוח (parsing). הכנסת השדות של כל מקור לאותם שמות שדה היא נרמול.

    לפני — השורה הגולמית

    Jan 15 10:23:45 server sshd[1234]: Failed password for admin from 192.168.1.100

    תחילה, ראה כיצד כלי השל הקלאסיים מושכים שדות בודדים. שמור את השורה למשתנה:

    RAW='Jan 15 10:23:45 server sshd[1234]: Failed password for admin from 192.168.1.100'

# timestamp = first 3 space-separated fields
echo "$RAW" | awk '{print $1, $2, $3}'
# host = field 4
echo "$RAW" | awk '{print $4}'
# service = field 5, with the [pid] and colon stripped off
echo "$RAW" | awk '{print $5}' | sed 's/\[.*//'
# username = the word after "for"
echo "$RAW" | grep -oP '(?<=for )\S+'
# source IP = the word after "from"
echo "$RAW" | grep -oP '(?<=from )\d+\.\d+\.\d+\.\d+'
    חמש הפקודות מדפיסות, לפי הסדר: Jan 15 10:23:45, server, sshd, admin, ו-192.168.1.100.

    כעת בצע את כל העבודה בבת אחת עם מנתח Python קצר. צור את הסקריפט:

    cat > ~/parse_log.py << 'EOF'
#!/usr/bin/env python3
import re, json, sys

raw = ("Jan 15 10:23:45 server sshd[1234]: "
       "Failed password for admin from 192.168.1.100")

# One regex captures every field we care about
pattern = re.compile(
    r'^(?P\w{3}\s+\d+\s[\d:]+)\s'
    r'(?P\S+)\s'
    r'(?P\w+)\[\d+\]:\s'
    r'(?PFailed password|Accepted password)\sfor\s'
    r'(?P\S+)\sfrom\s'
    r'(?P\d+\.\d+\.\d+\.\d+)'
)

m = pattern.match(raw)
if not m:
    print("Line did not match the parser", file=sys.stderr)
    sys.exit(1)

event = m.groupdict()
event["event"] = ("authentication_failure"
                  if event["event"] == "Failed password"
                  else "authentication_success")

print(json.dumps(event, indent=2))
EOF
python3 ~/parse_log.py

    אחרי — ה-JSON המנורמל

    {
  "timestamp": "Jan 15 10:23:45",
  "host": "server",
  "service": "sshd",
  "event": "authentication_failure",
  "user": "admin",
  "src_ip": "192.168.1.100"
}
    python3 ~/parse_log.py מדפיס בדיוק את אובייקט ה-JSON שלמעלה — שישה שדות בעלי שם שחולצו משורה אחת של טקסט חופשי.
    זהו לב ליבו של SIEM. לכל מקור — חומת אש, DNS, Windows — יש פורמט גולמי שונה, אך לאחר הניתוח כולם חושפים את אותם שמות שדה (src_ip, user, event...). אותה סכמה משותפת היא מה שמאפשר לחיפוש אחד להתאים אירועים מכל מקור בבת אחת. SIEM אמיתי משלח מאות מנתחים כאלה (Splunk קורא להם "field extractions", ELK קורא להם "Logstash grok filters").
    אם Python מדפיס "Line did not match the parser", ה-regex ושורת הדוגמה לא מסכימים. שורת הדוגמה קבועה בתוך הסקריפט — אל תקליד אותה מחדש. אם ערכת את הסקריפט, הדבק שוב את הבלוק בדיוק כפי שמוצג.
  6. שלב 6 — מושג: Windows Event Forwarding (WEF)

    Linux משלח לוגים עם rsyslog (שלבים 2–4). ל-Windows יש מענה מובנה משלו: Windows Event Forwarding (WEF) — והחוזקה שלו היא שהוא לא צריך שום סוכן צד שלישי.

    כיצד זה עובד:

    1. SUBSCRIPTION   An admin defines, on a central server, which Event IDs
                  to collect (e.g. 4624/4625 logons, 4688 process creation).
2. WEC            That server runs the Windows Event Collector service and
                  publishes the subscription.
3. WEF (clients)  Every Windows endpoint runs the built-in WinRM service and
                  forwards matching events to the collector.
4. ForwardedEvents Collected events land in the collector's
                  "Forwarded Events" log, ready for a SIEM agent to read.
    מצבמי יוזםמתאים ביותר ל
    Source-initiated (דחיפה)כל נקודת קצה דוחפת לאוסףצי גדול, מחשבים ניידים — מוגדר פעם אחת דרך Group Policy
    Collector-initiated (משיכה)האוסף פונה לנקודות קצה ששמן מצויןסטים קטנים וקבועים של שרתים
    WEF משתמש ברכיבים שכבר נמצאים ב-Windows (WinRM + Event Collector), ולכן הוא "ללא סוכן". SOCs רבים עדיין מוסיפים forwarder קליל כגון Winlogbeat או Splunk Universal Forwarder מעל לכך — שקורא את "Forwarded Events" באוסף, או קורא את ה-Event Log ישירות בכל נקודת קצה — כדי לשלח את האירועים הלאה ל-SIEM.
  7. שלב 7 — מושג: אוטומציית SOAR וערימת ה-ELK

    SOAR — Security Orchestration, Automation and Response

    SIEM מזהה. פלטפורמת SOAR פועלת — היא מריצה playbooks, שהם תהליכי תגובה מתוסרטים וניתנים לחזרה, כך שאנליסטים לא עושים את אותן לחיצות ידניות עבור כל התראה.

    דוגמה — playbook אוטומטי להתראת פישינג:

    TRIGGER:  A user reports a suspicious email, or the SIEM raises a
          "phishing" alert.

PLAYBOOK STEPS (run automatically):
  1. Extract URLs, attachments, and the sender from the email.
  2. Detonate attachments in a sandbox; check URLs against
     threat-intel feeds (VirusTotal, URLhaus).
  3. If verdict = malicious:
       a. Search every mailbox for the same email and delete copies.
       b. Block the sender domain at the mail gateway.
       c. Block the malicious URL/IP at the proxy and firewall.
       d. Open a ticket and assign it to a SOC analyst.
  4. If verdict = clean: close the alert, notify the reporting user.

RESULT:   A response that took an analyst 30+ minutes now finishes
          in under a minute, the same way every time.
    SOAR הוא שלב "6. ACTION" של הצינור משלב 1. האדם עדיין אחראי על שיקולי דעת; SOAR מסיר את העבודה המכנית החוזרת.

    ELK — ערימת SIEM חלופית

    הצינור במעבדה זו ניטרלי מבחינת ספק. מימוש קוד פתוח נפוץ מאוד שלו הוא ערימת ELK (Elastic):

    רכיבשלב בצינורתפקיד
    Beatsאיסוףמשלחים קלילים בכל מארח (Filebeat ללוגים, Winlogbeat לאירועי Windows)
    Logstashניתוחמקבל לוגים גולמיים ומריץ grok filters כדי לחלץ ולנרמל שדות — עבודת שלב 5
    Elasticsearchאחסוןמאנדקס את האירועים המנורמלים לחיפוש מהיר של טקסט מלא ושדות
    Kibanaאנליזהדשבורדים, ויזואליזציות, וממשק החיפוש לאנליסטים

    אנליסטים שואלים SIEM בשפת חיפוש. שתי השפות שתפגוש בהן הכי הרבה:

    שפהבשימוש על ידימציאת התחברויות כושלות מ-IP אחד
    SPL (Search Processing Language)Splunkindex=linux event=authentication_failure src_ip=192.168.1.100 | stats count
    KQL (Kibana Query Language)Elastic / Kibana (גם Microsoft Sentinel)event:"authentication_failure" and src_ip:"192.168.1.100"
    SPL הוא בסגנון צינור: חיפוש, ואז פקודות | שמשנות את התוצאות — מאוד אקספרסיבי לסטטיסטיקות וקורלציה. KQL קרוב יותר לביטוי סינון: פשוט יותר לקריאה, מהיר ל"מצא לי את האירועים האלה". שתיהן נשענות לחלוטין על שמות השדות המנותחים משלב 5 — ללא ניתוח, אין שאילתה.
  8. שלב 8 — ניקוי (החזרת המכונה למצבה)

    המעבדה הסתיימה. הסר את תצורת האוסף כדי ש-Kali תחזור להתנהגות הרישום המקורית שלה:

    sudo rm /etc/rsyslog.d/10-central.conf
sudo systemctl restart rsyslog

    אופציונלי, הסר את ארטיפקטי המעבדה:

    sudo rm -rf /var/log/central
rm ~/parse_log.py
    לאחר ההפעלה מחדש, sudo ss -lntup | grep 514 לא מדפיס כלום — המאזין הרשתי נעלם ו-rsyslog חזר לרישום מקומי בלבד.

שאלות חזרה

  1. ציין את ששת שלבי זרימת הנתונים ב-SIEM לפי הסדר, ואמור באיזה שלב מטפל rsyslog.
  2. בשלב 3, מה משנה האפשרות -n ב-logger -n 127.0.0.1 -P 514 בהשוואה לפקודת logger פשוטה?
  3. מה ההבדל בין ניתוח (parsing) לנרמול? מדוע נרמול חשוב כאשר SIEM קולט גם חומת אש וגם שרת DNS?
  4. מדוע Windows Event Forwarding מתואר כ"ללא סוכן", ואילו שני שירותי Windows מובנים גורמים לו לעבוד?
  5. תן שתי פעולות playbook שפלטפורמת SOAR הייתה מבצעת אוטומטית כאשר אימייל מאומת כפישינג.
  6. התאם כל רכיב ELK (Beats, Logstash, Elasticsearch, Kibana) לשלב שלו בצינור ה-SIEM.
  7. המנתח משלב 5 הפך שורת לוג אחת ל-JSON. מדוע SIEM יכול לקשר אירועים הרבה יותר טוב מול ה-JSON הזה מאשר מול שורת הטקסט הגולמית?

רשימת הכנה למדריך

הכן את הדברים הבאים לפני השיעור כך שתלמידים לעולם לא יחפשו דבר:

[ ] Kali Linux VM is built, boots to desktop, terminal opens
[ ] Student user has sudo (default: kali / kali) -- verified with: sudo -v
[ ] rsyslog is installed and running:  systemctl status rsyslog
[ ] Package 'rsyslog' modules imudp/imtcp available (default Kali -- confirm)
[ ] logger, awk, sed, grep, tail, python3 all present (default Kali -- confirm)
[ ] No firewall rule blocks loopback TCP/UDP 514 (default Kali: none)
[ ] Port 514 is free before the lab:  sudo ss -lntup | grep 514  -> empty
[ ] /etc/rsyslog.d/ is writable with sudo and auto-loaded by rsyslog
[ ] Snapshot the clean VM state so the lab can be reset between cohorts
[ ] Dry-run Steps 2-5 once end to end; confirm /var/log/central/ fills
[ ] Confirm Step 8 cleanup fully removes the listener (ss | grep 514 empty)
אין קבצי תוכנה זדונית בשימוש במעבדה זו, ולכן אין החרגת אנטי-וירוס להכין מראש ואין שלב 0. שינוי המצב היחיד הוא קובץ תצורת rsyslog בודד מסוג drop-in, המוסר במלואו בשלב 8.

סיכום

SIEM הוא צינור בן שישה שלבים: מקורות → איסוף → ניתוח → אחסון → אנליזה → פעולה. במעבדה זו הקמת את שלב האיסוף עם rsyslog על פורט 514, ייצרת וצפית באירועים חיים עם logger ו-tail -f, ובנית את שלב הניתוח ביד — בהפיכת שורת syslog גולמית אחת ל-JSON מנורמל. אותה סכמת שדות משותפת היא מה שהופך SIEM לחזק: היא מאפשרת לשאילתה אחת להתאים אירועים מכל מקור. WEF מכניס את Windows לצינור ללא סוכן, ELK הוא מימוש קוד פתוח נפוץ של הערימה כולה, ו-SOAR מאמת את שלב הפעולה הסופי.

סיכום הקורס: ראית עכשיו ניתוח ראשוני של תוכנה זדונית, ניתוח חי של נקודת קצה, פורנזיקת זיכרון, וצינור ה-SIEM — ליבת העבודה היומיומית ב-SOC.
